1. Introduction & Project Overview

UniGuard SIEM is a lightweight, full-stack Security Information and Event Management (SIEM) web application purpose-built for university computer laboratory environments. It provides real-time ingestion, parsing, storage, and visual monitoring of raw network access log data, with automated brute-force intrusion detection and a live dashboard interface.

The system was designed from the ground up to demonstrate core cybersecurity engineering principles — including log normalisation, stateful threat detection using rolling time windows, and responsive security dashboarding — using a minimal, dependency-light technology stack accessible to any institution.

Unlike enterprise SIEM platforms (Splunk, IBM QRadar, Microsoft Sentinel) that require significant infrastructure overhead, UniGuard SIEM runs entirely on a single machine with no external services, making it ideal for educational deployment, security lab exercises, and proof-of-concept demonstrations.

2. Problem Statement

University computer labs present a unique cybersecurity challenge. With dozens of shared workstations accessed by hundreds of different users, detecting malicious activity — particularly brute-force login attempts against privileged accounts — requires continuous log monitoring that most institutions currently perform manually or not at all.

Core Threat: A malicious actor sitting at any lab workstation (or operating remotely on the university LAN) can repeatedly attempt to authenticate as a privileged user such as admin_root. Without automated detection, these attempts generate no visible alert and may succeed before any administrator notices.

Specifically, this project addresses the following gaps in a typical university lab environment:

  • No centralised collection point for access log data across heterogeneous workstations
  • No automated detection of high-frequency failed login patterns from a single source
  • No real-time visual interface for security staff to monitor the state of the network
  • No structured format or database for storing and querying historical login events

3. Objectives

  1. Build a REST API endpoint capable of ingesting raw key-value log strings via HTTP POST from any source on the network.
  2. Implement a regex-based log parser to extract structured fields (Status, User, SrcIP, Workstation) from unstructured log strings.
  3. Persist all parsed log events to a local SQLite database with timestamping for temporal analysis.
  4. Implement a rolling-window brute-force detector that flags any source IP generating ≥ 5 failed logins within a 2-minute window, regardless of the target username.
  5. Design a dark-themed responsive web dashboard that updates in real time without page reloads, displaying live event logs, metric counters, and a flashing alert panel.
  6. Provide companion testing utilities (traffic generator and file injector) to simulate both normal and attack traffic for validation purposes.

6. Technical Implementation

6.1 Log Ingestion Endpoint (POST /api/logs)

The primary data entry point accepts either a JSON body {"raw": "..."} or a plain-text POST body for maximum compatibility with different log shippers. An empty payload returns HTTP 400; a payload that does not match the expected log format returns HTTP 422 (Unprocessable Entity).

6.2 Regex Log Parser

Log strings follow a loosely-structured key-value format. The parser uses a single compiled regular expression with four named capture groups:

LOG_PATTERN = re.compile( r'Status="(?P<status>[^"]+)".*?' r'User="(?P<user>[^"]+)".*?' r'SrcIP="(?P<src_ip>[^"]+)".*?' r'Workstation="(?P<workstation>[^"]+)"', re.IGNORECASE | re.DOTALL, )

The re.IGNORECASE flag allows fields to appear in any case variant. The re.DOTALL flag permits matching across newlines in multi-line payloads. Named groups provide clean extraction without positional index fragility. All extracted Status values are normalised to uppercase before storage to ensure consistent filtering.

6.3 SQLite Database Schema

All parsed events are stored in a single logs table:

6.4 Frontend Dashboard

The dashboard (index.html) is a single-page application rendered by Flask's render_template(). It uses Tailwind CSS (CDN) for styling and pure Vanilla JavaScript for all dynamic behaviour — no frontend framework is required.

Three independent poll loops run on a shared 3-second interval, each fetching a separate API endpoint:

  • Log Stream — fetches GET /api/logs, inserts only new rows (tracked by ID set), new rows flash blue on entry
  • Metric Cards — fetches GET /api/metrics, updates Total / Success / Fail counters
  • Alert Panel — fetches GET /api/alerts, applies a CSS pulse animation and red colour scheme when any alert is active

7. Security Detection Logic

7.1 Brute-Force Detection Algorithm

The core detection mechanism implements a stateful rolling time-window counter. On every incoming FAIL log, the backend queries the database for the count of FAIL events originating from the same SrcIP within the last 2 minutes:

SELECT COUNT(*) AS attack_count FROM logs WHERE status = 'FAIL' AND src_ip = ? -- the specific attacker IP AND timestamp >= ? -- rolling 2-minute window

If attack_count >= 5, the function returns True and the API response includes "alert": true. The dashboard's polling endpoint performs the same query across all IPs simultaneously using GROUP BY src_ip HAVING COUNT(id) >= 5.

Design decision — username-agnostic detection: The alert fires based solely on SrcIP, not on the combination of SrcIP + username. This is intentional — it catches credential-stuffing attacks where an attacker cycles through multiple target usernames from one machine, which a per-user threshold would miss entirely.

7.2 Alert Lifecycle

  • ✓

    Normal State

    Dashboard shows green "No active alerts — system nominal." The Alerts Panel border is slate-grey.

  • !

    5th FAIL from Same IP Within 2 Minutes

    Alert threshold crossed. Next dashboard poll (within 3 s) activates the CSS pulse animation, turns the panel bright red, and displays the offending IP with its attack count.

  • ↺

    Automatic Expiry

    The rolling window moves forward continuously. If no new FAIL events arrive from that IP, the 2-minute window expires and the alert clears itself — no manual reset required.

✓ Scenario 2 — Brute-Force Trigger: 8 FAIL POSTs from 10.199.45.12 sent within ~1.6 seconds. Alert panel turned red and pulsed after the 5th request. Correct IP and attack count displayed. Alert expired automatically after 2-minute window elapsed with no new FAILs.
✓ Scenario 3 — Malformed Payload: POST with missing fields returned HTTP 422 with a descriptive error message. Server continued processing subsequent valid requests normally.
✓ Scenario 4 — File Injection: Running file_injector.py against the 20-line log file reproduced the full attack timeline — baseline → brute-force alert → baseline return — with per-line console output and inline alert flags.

12. Conclusion

UniGuard SIEM demonstrates that a functional, real-time security monitoring system can be built using only standard Python libraries, a file-based database, and modern CSS — without any enterprise tooling or cloud infrastructure. The project successfully met all six stated objectives: log ingestion, regex-based field extraction, persistent storage, rolling-window brute-force detection, a live dark-theme dashboard, and a full suite of testing utilities.

The most significant technical outcome is the alert detection engine: by anchoring detection to source IP address alone across a sliding 2-minute window — rather than per-username or cumulative all-time counts — the system accurately models the behaviour of real brute-force and credential-stuffing attacks while avoiding both false positives (legitimate retries) and stale false positives (old historical failures).

The project establishes a solid foundation that could be extended into a production-grade tool with the enhancements outlined in Section 11. As a standalone educational platform, it provides a hands-on, fully operational example of the core principles underlying commercial SIEM products.
